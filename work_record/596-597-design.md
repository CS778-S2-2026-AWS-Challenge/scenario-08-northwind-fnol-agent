# Issues 596-597 Design Record

This record captures the agreed design decisions for Week 6 P6.1 and P6.2 before implementation.

## Confirmed decisions 1-8

1. **Model-aware context budgets.** The context contract supports different model limits rather than assuming one universal window. A model profile declares `context_window_tokens`, `max_input_tokens`, `max_output_tokens`, and reserved space for system instructions, tool results, and structured output. Capacity is labelled `verified`, `configured`, or `unknown`. Qwen's current connection is usable but its boundary remains conservatively configured and marked unknown until verified; no provider capability is implied by configuration alone.

2. **Six plus one behaviour shape.** The brief defines six main behaviour families: field collection, natural-language correction, progress explanation, RAG/policy/history query, third-party service suggestion, and professional handoff. Confirmation is a cross-cutting gate, not a seventh business route.

3. **Staff model selection is session-bound.** The Workbench may select only a backend-published, available Model Profile. The browser never submits provider, endpoint, or credentials. The selected profile is persisted on the Staff Agent session and every assistant message records the profile actually used. Claimant sessions keep their own server-selected profile; claimant UI does not expose model selection.

4. **Context is persisted fully and restored selectively.** Claim State, unresolved questions, pending work, branch, next action, and permissions are always available. Recent messages and summaries are included within the selected model budget. Full immutable `MessageRecord` content is loaded only when a source reference is needed for correction, conflict, explanation, evidence checking, or missing semantics. A resumed session compares its `context_revision` with the latest Claim revision, recomputes unresolved work and the next step, and does not create a duplicate working Claim.

5. **Assertion conflicts remain source-preserving.** Runtime classifies a new statement as equivalent, compatible refinement, explicit correction, material conflict, different semantic field, or irrelevant. The selected Claim fact remains authoritative; assertions retain their source references. Corrections supersede the prior assertion without deleting it. Material conflicts create clarification or professional-review work and never become a fraud conclusion by themselves.

6. **First clear ordinary human request transfers.** The first unambiguous natural-language request for a person creates a standard-priority handoff. Repeated requests, urgency, distress, or accessibility needs still transfer immediately and may raise priority. This is a normative behaviour change and must be reflected in the specification, Runtime enforcement, prompt, and tests rather than in prompt text alone.

7. **Claimant `@agent` is removed from the target path.** Claimant conversations use ordinary natural language. Staff assistance remains available through the dedicated Workbench Staff Agent session and ordinary staff questions; it is not an unrestricted autonomous chatbot. Any short-lived compatibility handling is removed from production code in this change, with no new claimant `@agent` entry point.

8. **Backend is authoritative.** Agent understanding, prompts, retrieval, and UI projections are connected to the existing backend contracts. The model may propose; only Runtime code validates authority, permissions, revisions, idempotency, visibility, and state effects. No fixture or prompt is a substitute for Claim State, persistence, or authorization.

## Scope for implementation

- P6.1: publish one context contract for claimant and staff runtimes, including visibility, source precedence, bounded history, model budgets, revision freshness, and unavailable-source semantics.
- P6.2: publish the six behaviour/action briefs plus the confirmation gate, with triggers, inputs, outputs, allowed actions/tools, authority, prohibited effects, Claim State effects, visibility, failure handling, handoff rules, and repeatable proof.
- Persist Staff Agent model selection on its session and expose the selected profile in the session/message contract without exposing credentials.
- Remove claimant `@agent` parsing and bypass logic; normal claimant messages continue through the standard Runtime path.
- Keep existing authoritative Claim State, persistence adapters, model gateway, and token/component standards. Any new shared API or persistence field is updated in `docs/api.md`, `docs/persistence-schema.md`, OpenAPI snapshot, consumers, and tests in the same change.

## Explicit non-goals

- No second Claim State or parallel persistence model.
- No provider-specific authority in prompts, no credential in browser/API payloads, and no claim of live provider readiness from a configured profile.
- No new claimant `@agent` capability, unrestricted staff automation, or automatic execution of staff drafts.
- No replacement of the existing compatibility transport until its documented migration gate is met.

## Acceptance evidence

- Contract tests prove model profile selection is stored and reused for a Staff Agent session, and a message cannot override it.
- Context tests prove claimant scope isolation, staff multi-Claim scope, bounded history, source-linked selective recovery, stale-session re-plan, and explicit unavailable-source labels.
- Behaviour tests prove all six behaviours and the confirmation gate declare valid Runtime actions, authority/prohibited effects, failure and handoff semantics.
- Regression tests prove claimant `@agent` text is treated as ordinary user text and no claimant-specific `@agent` branch remains.
- The final PR records exact-head local evidence and CircleCI results.
